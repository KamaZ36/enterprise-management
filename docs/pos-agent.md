# Техническое задание: агент сбора продаж DoKa (C#, Windows)

> Статус: черновик v1
> Область: только клиентская часть (C#). Серверный модуль `pos` разрабатывается отдельно,
> его HTTP-контракт зафиксирован в разделе 9 и считается внешней зависимостью.

---

## 1. Назначение и границы

Агент — служба-«сборщик», которая крутится на кассовом терминале под Windows 11,
находит файлы журнала продаж, которые выгружает DoKa, разбирает их и отправляет
на сервер `myasnaya_derevnya`. Сервер уже сам решает, что списать со склада.

### Что агент делает

- Следит за папкой `C:\DoKa\BASE` (путь настраивается).
- Находит файлы `Обмен_Продаж_<ИНН>_<дд.ММ.гггг>_<чч.мм.сс>.xml`.
- Разбирает их, нормализует и складывает в локальную очередь (SQLite).
- Отправляет чеки на сервер батчами, с ретраями и дедупликацией.
- Показывает состояние через GUI и трей, ведёт логи.

### Что агент НЕ делает (важно)

- **Не читает** `Doka4_db.accdb` и вообще не открывает базу Access.
- **Не пишет** ничего в папку DoKa. Только чтение.
- **Не трогает** `УведЗагр.xml` — это часть штатного обмена DoKa, запись в него может
  сломать выгрузку.
- **Не считает** остатки, себестоимость, техкарты, единицы измерения. Это всё на сервере.
- **Не фильтрует** чеки по бизнес-правилам (кроме технической дедупликации).
  Агент — «тупой и честный транспорт»: что в файле, то и уехало.

Принцип: любое изменение бизнес-логики не должно требовать обновления агента на кассах.

## 2. Контекст: как устроена касса

DoKa 4 — Access-приложение. Раз в сутки (около 17:50–18:00) она кладёт в `BASE`
XML-файл журнала продаж. Файл содержит **последние 4 дня** чеков, а не только новые.

Наблюдаемые факты (проверено на реальных данных кафе и магазина):

| Факт | Значение |
|---|---|
| Кодировка | `windows-1251`, без BOM |
| Размер файла | 0.9–1.1 МБ (кафе), 0.37–0.50 МБ (магазин) |
| Чеков в файле | 137–227 |
| Строк в файле | 290–637 |
| Периодичность | 1 раз в сутки вечером |
| Дубликаты | 2 файла в день; различаются только `НаимФайл`/`ВремяДок`, состав чеков идентичен |
| Окно | 4 дня, перекрывается → один чек приходит в 4 файлах |
| `GUIDКасса` | уникален, совпадает с БД 1:1 |

Отсюда два обязательных свойства: **дедупликация по GUID чека** и **устойчивость
к повторной отправке одного и того же**.

## 3. Терминология

| Термин | Значение |
|---|---|
| Источник (`source`) | Касса DoKa, идентифицируется `ИДорг` (12 цифр, напр. `915612757914`) |
| Терминал / установка | Конкретный ПК с агентом (`install_id`) |
| Чек | Одна запись `СведЧек` в `ЖурналПродаж` |
| Строка | Одна запись `Строка` внутри `СведЧекСостав` |
| Товар DoKa | Запись `КарточкаТовара`, ключ `GUIDтовар` |

## 4. Технологический стек

| Слой | Выбор | Комментарий |
|---|---|---|
| Платформа | **.NET 10 (LTS)** | .NET 8 тоже допустим, но поддержка заканчивается в ноябре 2026 |
| GUI | **WPF** + `CommunityToolkit.Mvvm` | MVVM без тяжёлых фреймворков |
| Трей | `System.Windows.Forms.NotifyIcon` (`UseWindowsForms=true`) | Свой минимальный `TrayService` |

| Логи | **Serilog** + `Serilog.Sinks.File` + свой in-memory sink для UI | Ротация по дням |
| XML | `XmlReader` (потоково) | Файлы до 2 МБ, но потоково надёжнее |

| Шифрование ключа | `System.Security.Cryptography.ProtectedData` (DPAPI, `CurrentUser`) | Ключ не хранится в открытом виде |
| Тесты | xUnit + FluentAssertions | На реальных XML из `samples/` |
| Установщик | Inno Setup 6 | Per-machine, создаёт задачу автозапуска |
| Публикация | `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true` | Без установленного .NET на кассе |

```
       ▼                                      │
┌─────────────┐   ошибка парсинга → Error     │

       ▼                                      │
┌─────────────┐   5xx / сеть → retry с backoff│
│  Upload     ├───────────────────────────────┤
└──────┬──────┘                               │
       │ 200                                │
       ▼                                      │
┌─────────────┐                               │
│  MarkSent   ├───────────────────────────────┘
└─────────────┘
```

### Триггеры запуска

1. **По расписанию**: ежедневно в `18:05` локального времени (настраивается).
2. **Догон**: каждые `10` минут до `23:30`, если в очереди есть непроведённое
   или с прошлого успеха прошло больше суток.
3. **При старте приложения** (догон после перезагрузки).
4. **Вручную** из GUI/трея.

> Окно выгрузки DoKa — 4 дня. Если агент не работал дольше, данные восстанавливаются
> только из базы Access вручную. Поэтому алерт «нет успешной синхронизации > 24 ч»
> обязателен.

## 6. Формат входного XML

### 6.1. Общая структура

```xml
<?xml version="1.0" encoding="windows-1251"?>
<Файл НаимФайл="Выгрузка_Касса_360900586761_27.10.2026_17.57.04"
      ВерсФорм="1" ВерсПрог="Doka4(Кассовый модуль)" ТипДок="Журнал продаж"
      ДатаДок="27.10.2026" ВремяДок="17:57:04"
      НаимОрг="ИП Струк Е. Н." ИНН="360900586761" ИД="915612757914">
  <СправочникНоменклатуры КолВоЗаписей="94">
    <КарточкаТовара>…</КарточкаТовара>
  </СправочникНоменклатуры>
  <ЖурналПродаж>
    <СведЧек>…<СведЧекСостав><Строка/>…</СведЧекСостав></СведЧек>
  </ЖурналПродаж>
</Файл>
```

Порядок элементов в файле: сначала справочник, потом журнал. Парсер не должен
на это полагаться — читать оба блока и джойнить по `GUIDтовар` после.

### 6.2. Атрибуты корня `<Файл>`

| Атрибут | Пример | Использование |
|---|---|---|
| `НаимФайл` | `Выгрузка_Касса_…` | Лог, диагностика |
| `ВерсФорм` | `1` | Проверять, что `<= 1`, иначе warning |
| `ТипДок` | `Журнал продаж` | Проверять, иначе файл не наш |
| `ДатаДок` / `ВремяДок` | `27.10.2026` / `17:57:04` | `exported_at` |
| `ИНН` | `360900586761` | Лог; **не** ключ источника |
| `ИД` | `915612757914` | **`doka_org_id` — ключ источника** |

### 6.3. `<КарточкаТовара>` — справочник

Нужны только поля ниже, остальные игнорировать.

| Тег | Пример | Назначение |
|---|---|---|
| `GUIDтовар` | `1A537BD80C2E404890CB98625DB13B3E` | Ключ товара |
| `КодНом` | `52` | Внутренний код, для лога |
| `Наименование` | `Медовик` | Название |
| `КраткНаимТов` | `Медовик` | fallback названия |
| `Ед` | `кг` / `шт` | Единица; **передаётся как есть** |
| `Группа` | `Десерты` | Для диагностики маппинга |
| `Цена` | `1950` | Справочная, не использовать для расчётов |
| `ШтрихКод` | `` | Может быть пустым |
| `Архив` | `0` | `1` — товар архивный |

Справочник содержит только товары, встречающиеся в этом файле.

### 6.4. `<СведЧек>` — чек

| Тег | Пример | Обязательность | Примечание |

## 7. Правила нормализации

Всё, что ниже, агент обязан делать **до** отправки. Сервер тоже нормализует,
но контракт должен быть однозначным.

### 7.1. Идентификаторы

Каноническая форма: **верхний регистр, удалены все символы кроме `0-9A-F`**.

```
"27de7756-14ad-4d17-a482-b578611c605c915612757914"
   → "27DE775614AD4D17A482B578611C605C915612757914"   (44 символа)

"2CF47D3B-A782-47F4-A3D3-B79BC005363C"
   → "2CF47D3BA78247F4A3D3B79BC005363C"                (32 символа)
```

В реальных файлах формат гуляет: с дефисами и без, в разном регистре.
Нормализация обязательна, иначе дедупликация развалится.

### 7.2. Деньги

- Парсить как `decimal` с `CultureInfo.InvariantCulture`, но сначала заменить `,` на `.`.
- Переводить в **копейки** (`× 100`, округление `MidpointRounding.AwayFromZero`).
- В JSON передавать целым числом.
- Никогда не использовать `double`/`float`.

### 7.3. Количество

- Парсить так же (запятая → точка) в `decimal`.
- В JSON передавать **строкой** без потери точности: `"0.512"`.
- Не округлять и не конвертировать единицы.

### 7.4. Дата и время

- `occurred_at` = `Дата` + `Время` в локальной зоне терминала.
- Сериализовать в ISO 8601 **с offset**: `2026-10-24T08:02:26+03:00`.
- Часовой пояс брать `TimeZoneInfo.Local`, не хардкодить Москву.

### 7.5. Единицы измерения

Передавать `Ед` из справочника как есть (`кг`, `гр`, `шт`, `л`).
Сопоставление с внутренними единицами — задача сервера.

### 7.6. Кодировка и чтение файла

```csharp
Encoding.RegisterProvider(CodePagesEncodingProvider.Instance);
var enc = Encoding.GetEncoding(1251);
```

Открывать с `FileShare.ReadWrite | FileShare.Delete` — DoKa может держать файл.

### 7.7. Защитные проверки

| Проверка | Действие |
|---|---|
| `ТипДок != "Журнал продаж"` | Пропустить файл, warning |
| `ИД` не совпадает с настройкой `expectedDokaOrgId` | **Не отправлять**, ошибка |
| `sum(строк) != СумОпл` (допуск 1 копейка) | Отправить, но warning в лог и в поле `warnings` |
| Строка ссылается на неизвестный `Товар` | Отправить с `product_name = null`, warning |
| `КолВо <= 0` для `ТипЧек=1` | Отправить, warning |
| Файл не менялся < 5 секунд | Подождать следующий цикл |

## 8. Локальное состояние (SQLite)

Файл: `%ProgramData%\MyasnayaDerevnya\PosAgent\state.db`

```sql
CREATE TABLE files (
    id            INTEGER PRIMARY KEY,
    path          TEXT NOT NULL,
    name          TEXT NOT NULL,
    sha256        TEXT NOT NULL UNIQUE,
    size_bytes    INTEGER NOT NULL,
    exported_at   TEXT,
    first_seen_at TEXT NOT NULL,
    processed_at  TEXT,
    status        TEXT NOT NULL,   -- new | parsed | skipped | error
    error         TEXT
);

CREATE TABLE receipts (
    guid           TEXT PRIMARY KEY,      -- канонический
    file_id        INTEGER NOT NULL REFERENCES files(id),
    occurred_at    TEXT NOT NULL,
    kind           TEXT NOT NULL,         -- sale | return
    total_kopecks  INTEGER NOT NULL,
    payload_json   TEXT NOT NULL,         -- готовое тело для API
    status         TEXT NOT NULL,         -- pending | sent | rejected
    server_status  TEXT,                  -- posted | duplicate | pending_unmapped | pending_stock
    attempts       INTEGER NOT NULL DEFAULT 0,
    last_error     TEXT,
    next_attempt_at TEXT,
    sent_at        TEXT
);

CREATE TABLE meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

`payload_json` хранится целиком: файл живёт 4 дня и может исчезнуть, а очередь
должна уметь отправить чек и через неделю.

Индексы: `receipts(status, next_attempt_at)`, `files(sha256)`.

Миграции схемы — через `PRAGMA user_version` и простой список шагов.

## 9. HTTP-контракт с сервером

> Реализуется серверным модулем `pos`. Для разработки агента поднимается заглушка,
> возвращающая фиксированные ответы (см. 9.5).

### 9.1. Аутентификация

```
Authorization: Bearer <api-key>
X-Agent-Version: 1.0.0
X-Install-Id: 0f3c...            (UUID установки, генерируется один раз)
```

Ключ выдаётся на терминал при регистрации источника. В настройках хранится
в зашифрованном виде (DPAPI).

### 9.2. `POST /api/pos/receipts`

Запрос:

```json
{
  "source": {
    "doka_org_id": "915612757914"
  },
  "agent": {
    "install_id": "0f3c8a52-…",
    "version": "1.0.0",
    "hostname": "PC-CAFE-01",
    "clock_utc": "2026-10-27T15:05:00Z"
  },
  "file": {
    "name": "Обмен_Продаж_360900586761_27.10.2026_17.56.45.xml",
    "sha256": "…",
    "exported_at": "2026-10-27T17:56:45+03:00"
  },
  "receipts": [
    {
      "guid": "27DE775614AD4D17A482B578611C605C915612757914",
      "occurred_at": "2026-10-24T08:02:26+03:00",
      "kind": "sale",
      "payment_kind": "card",
      "total_kopecks": 25000,
      "subdivision_code": "1",
      "subdivision_name": "Торговый зал",
      "cashier": "Администратор",
      "shift": "422",
      "number": "1",
      "fd_number": "18747",
      "fp_number": "1603810978",
      "fn_number": "7380440902472099",
      "warnings": [],
      "lines": [
        {
          "guid": "A0F13AA47AF4468F8CD2EF7CF14E3674",
          "product_guid": "1A537BD80C2E404890CB98625DB13B3E",
          "product_name": "Медовик",
          "unit": "кг",
          "quantity": "0.512",
          "price_kopecks": 25000,
          "amount_kopecks": 25000,
          "discount_kopecks": 0,
          "barcode": null,
          "mark_code": null
        }
      ]
    }
  ]
}
```

Ограничения: не более **100 чеков** или **5 МБ** на запрос.

Ответ `200`:

```json
{
  "server_time": "2026-10-27T18:05:03+03:00",
  "batch_id": "0199a1b2-…",
  "results": [
    {
      "guid": "27DE7756…",
      "status": "posted",
      "message": null
    }
  ]
}
```

`batch_id` — идентификатор принятого пакета, нужен только для разбора инцидентов;
агенту его хранить не обязательно. `server_time` — время сервера, по нему агент
считает дрейф часов.

`status`:

| Значение | Что значит для агента |
|---|---|
| `posted` | Принят и проведён. Отметить `sent`. |
| `duplicate` | Уже был. Отметить `sent`. |
| `pending_unmapped` | Принят, но товар не размечен. **Отметить `sent`** — сервер сам доведёт. |
| `pending_stock` | Принят, но не хватает остатка. **Отметить `sent`**. |
| `rejected` | Не принят (битые данные). Отметить `rejected`, не ретраить. |

Ключевое правило: **только транспортные ошибки (сеть, 5xx) ведут к повтору**.
Любой `200` — это доставка, дальше ответственность сервера.

### 9.3. `POST /api/pos/heartbeat`

Раз в 5 минут и после каждой синхронизации:

```json
{
  "install_id": "0f3c…",
  "version": "1.0.0",
  "hostname": "PC-CAFE-01",
  "source": { "doka_org_id": "915612757914" },
  "status": "ok",
  "pending_receipts": 0,
  "last_success_at": "2026-10-27T18:05:03+03:00",
  "last_error": null,
  "clock_utc": "2026-10-27T15:05:00Z"
}
```

Ответ: `200` + `server_time`. Используется для проверки ключа и дрейфа часов.

### 9.4. Коды ошибок

| Код | Поведение агента |
|---|---|
| `200` | Разобрать `results` |
| `400`, `422` | Пометить батч `rejected`, показать ошибку, **не ретраить** |
| `401`, `403` | Остановить отправку, статус «Неверный ключ», алерт |
| `404` | Источник не зарегистрирован → остановить, показать инструкцию |
| `409` | Считать как `duplicate` (идемпотентность) |
| `429` | Ждать `Retry-After`, ретраить |
| `5xx`, таймаут, DNS | Ретрай с backoff |

### 9.5. Заглушка сервера для разработки

Минимальный Kestrel-проект `PosAgent.MockServer` (или `dotnet run` из шаблона):
принимает оба эндпоинта, валидирует JSON-схему, возвращает `200` и эхо `results`.
Позволяет проверить весь цикл без бэкенда.

## 10. Надёжность

### 10.1. Ретраи

- Экспоненциальный backoff с джиттером: `30с → 1м → 2м → 5м → 10м → 15м`, дальше 15м.
- Максимум попыток на чек — не ограничен, но после 1 часа непрерывных ошибок —
  статус «Проблема» и уведомление в трее.
- `429` — приоритет `Retry-After`.

### 10.2. Дедупликация

Три уровня:

1. **Файл** — `sha256` в `files`. Ловит только точные побайтовые повторы
   (скопировали, переложили, переотправили). Пары файлов за один день
   различаются атрибутами шапки, поэтому этот уровень их **не** отсекает.
2. **Чек** — `receipts.guid` PRIMARY KEY. **Основной механизм**: и дубли
   за день, и перекрытие 4-дневного окна закрываются здесь.
3. **Сервер** — `unique(source_id, external_guid)`. Последний рубеж.

### 10.3. Атомарность

- Парсинг файла → запись чеков в SQLite в одной транзакции.
- Отправка → после `200` обновить статусы в одной транзакции.
- Падение между отправкой и обновлением статуса безопасно: сервер вернёт `duplicate`.

### 10.4. Прочее

- Single-instance: `Mutex("Global\\MyasnayaDerevnya.PosAgent")`.
- Часы: если расхождение с `server_time` > 5 минут — предупреждение в UI.
- Сеть: `HttpClient` с `Timeout = 30с`, отдельный таймаут на подключение 10с.
- Диск: если `state.db` недоступна — работать нельзя, показать ошибку, не терять молча.
- Папка источника на сетевом диске (`Z:`) — обрабатывать `IOException` как временную.

## 14. Логирование

## 15. Безопасность

- Только исходящие HTTPS-соединения. Входящих портов не открывать.
- API-ключ — только в защищённом виде, никогда в логах и в диагностическом архиве.
- Не запускать от администратора. Достаточно прав на чтение папки DoKa

- Подписать exe сертификатом (по возможности) — иначе антивирус будет ругаться.
- Рекомендация в инструкции: добавить папку агента в исключения антивируса.

## 18. Тестирование

### Эталонные файлы

Скопировать в `samples/` из репозитория:

| Файл | Чеков | Строк |
|---|---|---|
| `DoKa_кафе/BASE/Обмен_Продаж_360900586761_27.10.2026_17.56.45.xml` | 209 | 637 |
| `DoKa_магазин/BASE/Магазин/Обмен_Продаж_360900586761_27.10.2026_17.59.06.xml` | 137 | 290 |

На них фиксируются ожидаемые счётчики в тестах парсера. Файлы нельзя
редактировать (в частности, перекодировать) — они проверяют cp1251 и запятые.

### Юнит-тесты (обязательно)

1. **Парсер** на 4 реальных файлах из `samples/`:
   - количество чеков и строк совпадает с эталоном;
   - сумма строк = сумме чеков (допуск 1 копейка);
   - канонизация GUID (с дефисами, без, нижний регистр);
   - `322,8` → `32280` копеек;
   - `0,512` → `"0.512"`;
   - `8:02:26` → `2026-10-24T08:02:26+03:00` (при подменённой зоне).
2. **Дедупликация**: два файла за один день (различаются только шапкой) →
   второй разбирается, но ни один чек не дублируется; чек из соседнего дня
   (4-дневное окно) → тоже не дублируется.
3. **Очередь**: падение между отправкой и записью статуса → повтор даёт
   `duplicate`, данные не теряются.
4. **Ретраи**: 500 → 200, проверка backoff; 401 → остановка.
5. **Конфиг**: битый JSON → бэкап, состояние «Не настроен».

### Ручные проверки

- Сухой прогон на реальной кассе без отправки.
- Отключить сеть на 10 минут → очередь растёт, после включения уходит.
- Убить процесс во время отправки → после старта ничего не потеряно.
- Перезагрузка ПК → агент поднялся свёрнутым, догнал очередь.

## 19. Критерии приёмки

1. Агент устанавливается одним exe-установщиком, запускается без администратора,
   стартует при входе в Windows свёрнутым в трей.
2. Через 1 минуту после появления нового `Обмен_Продаж_*.xml` чеки уходят на сервер.
3. Повторный запуск и повторная отправка того же файла не создают дублей
   ни на клиенте, ни на сервере.
4. При отсутствии сети данные копятся локально и уходят после восстановления,
   без потерь и без дублей.
5. GUI показывает актуальный статус, очередь, последнюю ошибку; лог фильтруется
   и экспортируется.
6. Сухой прогон показывает корректные счётчики и **ничего не отправляет**.
7. Смена API-ключа и адреса сервера применяется без перезапуска.
8. Логи не содержат ключа и полного содержимого чеков.
9. При замене ПК достаточно установить агент и ввести ключ — история не ломается.

## 21. Открытые вопросы

1. **Возвраты.** В выборке XML за 4 дня чеков с `ТипЧек=-1` не было. Нужно
   подтвердить на реальной кассе, что возвраты вообще попадают в выгрузку.
   Если нет — потребуется отдельный канал (чтение БД или ручной ввод).
   Сервер v1 сохраняет возвраты со статусом `ignored` и по складу их не проводит;
   для полноценного проведения потребуется движение `RETURN` в inventory.
2. **Несколько касс на одну папку.** Если два ПК пишут в общий `Z:\BASE`,
   агент ставить на одну машину или на обе? Сейчас предполагается «одна папка —
   один агент».
3. **Несколько источников на одном ПК.** Если на терминале две базы DoKa,
   поддерживать ли несколько профилей источника в одном агенте (v1 — один).
4. **Прокси.** Нужен ли HTTP-прокси в настройках (сейчас нет).
5. **Сертификат.** Самоподписанный сертификат сервера — разрешать или нет.
6. **Ключ и смена пользователя Windows.** DPAPI привязан к пользователю.
   Если на кассе несколько учёток — решить: один пользователь или
   `LocalMachine`-scope.

## 22. Серверная часть (реализовано в v1)

Модуль `pos` в бэкенде (`src/myasnaya_derevnya/modules/pos`) принимает чеки
и проводит их по складу. Схема БД — `pos` (`sources`, `agents`, `import_batches`,
`receipts`, `receipt_lines`, `product_map`).

### 22.1. Эндпоинты агента

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/pos/receipts` | Пакет чеков (до 100) |
| `POST` | `/api/pos/heartbeat` | Отметка агента |

Оба требуют `Authorization: Bearer <api-key>` **и** `X-Install-Id`. Неизвестный
или отозванный ключ — `401`; ключ, выданный другому `ИДорг`, — `403`;
неизвестная установка привязывается к агенту при первом успешном запросе.

### 22.3. Статусы чека на сервере

`new` → `needs_mapping` → `ready` → `posted`; отдельно `needs_stock`, `failed`,
`ignored`. Наружу агенту отдаются `posted`, `duplicate`, `pending_unmapped`,
`pending_stock`, `rejected` (см. 9.2).

- `needs_mapping` — хотя бы одна строка без номенклатуры. После `PUT product-map`
  сервер проставляет номенклатуру во все непринятые чеки источника и переводит
  их в `ready`.
- `needs_stock` — не хватило остатка; чек можно провести повторно после
  поступления товара (`POST .../post` или `POST /receipts/post-pending`).
- `ignored` — возвраты (`kind=return`) и пустые чеки. Возвраты сохраняются,
  но по складу не проводятся: в v1 нет движения `RETURN`.
